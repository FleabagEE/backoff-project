# Live sensor / slide diagnosis — October 19, 2026

**Finding:** the model recognizes the scratch continuation as rub, but transient
knock outputs at its start trigger C's next-slide action before rub arrives.
C then rejects rub until neutral has been confirmed. No retraining, model,
gate, capture, feature or live decision changes were made during these tests.
This controlled result supersedes earlier informal reports that all actions
worked. It is not a completed acceptance test.

## Live versus offline parity

Each batch has 769 captured FFT windows, capture status count0, median update
gap47ms (~21.3 updates/s). Both raw labels and gate outputs match offline replay
in **769/769 windows for each batch**. Maximum decision-score discrepancy is
4.47e-15 (floating-point rounding), with no class changes. Same artifact pair
and original 1200-feature arrays are used; no second log/scaler is applied.

Knock UDP: 277 sent, 277 received. Scratch UDP: 284 sent, 284 received. Payload
multisets match exactly, including timestamps and heartbeat markers. No missing
messages were observed in these runs. This does not establish general zero-loss
networking or measured physical-to-slide latency.

The recordings save FFT feature inputs, RMS/peak and model outputs, **not PCM**.
Parity rules out different classification of the exact same inputs; it cannot
recompute FFTs, prove unchanged hardware coupling, or make temporally smoothed
features independent of acquisition/update cadence. Logging adds overhead.

All five scratch event-mean predictions are rub. Thus the previous96% grouped
take CV measures different decision behavior from first per-window triggering;
it never promised that scratch windows contain no knock transients.

## Replay-only alternatives (no live fix applied)

Each candidate reuses the saved features and unchanged model, then C's actual
LabelSender change/heartbeat logic and GestureGate. Delivery is simulated with
zero latency/loss at recorded feature timestamps and no page bounds. Baseline
sender heartbeat counts can differ from real send timing because scoring/logging
and receive jitter are absent; actual logged receiver decisions remain the
authority. Per-action event outcomes agree with the observed baseline.

Success requires exactly one intended action and no wrong/extra action per slot.

| Candidate | Knock correct /5 | Scratch correct /5 | Interpretation |
|---|---:|---:|---|
| Current first-window gate + frontend | 5 | 0 | Onset K wins |
| K_knock=2, K_rub=6 | 5 | 1 | Scratch often starts with >=2 K windows |
| Pending knock delay250ms, rub priority after2 R windows | 5 | 4 | Isolated early K in scratch5 still wins before delayed rub |
| Only reduce slide cooldown .8 -> .4s | 5 | 0 | Neutral re-arm still prevents rub |
| Only reduce slide cooldown .8 -> 0s | 5 | 0 | Same issue |
| Detect event, average active-window scores through onset+1.5s | 5 | 5 | Best replay; suppresses onset transients, adds ~1.5s decision latency |

**Recommendation:** use event-level decisions as the next candidate for a
prospective live test, keeping the model and gate fixed. It matches the decision
unit used for take CV and wins on these recordings. A250ms knock delay is a
lower-latency alternative but did not solve every recorded case. A simple K2/R6
rule or cooldown change is insufficient here. No new live implementation has
been deployed. These ten actions are now development data; replay10/10 is NOT
an independent final test result. Fresh actions, quiet and adversarial inputs
must validate a proposed fix, especially weak knocks and event latency.
